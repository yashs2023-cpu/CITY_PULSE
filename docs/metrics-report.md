# CITY-PULSE T2 — Software Metrics + System Quality Report

## 1. Objective

The T2 work evaluates CITY-PULSE with respect to code quality, system reliability, performance, data freshness, trust, test quality, and operational workflow. The scope follows the team plan: GQM, reproducible code metrics, System Quality dashboard evidence, coverage/defect tracking, and a final metrics report.

## 2. GQM summary

The goal is to evaluate and improve the CITY-PULSE system from the development/QA viewpoint. Questions cover structural code quality, provider reliability, data-state quality, trust, Authority workflow efficiency, test quality, and unresolved defects. The detailed plan is in `docs/gqm-plan.md`.

## 3. Code quality evidence

The existing code-analysis run reported **0 errors and 4 warnings**. Complexity findings included `createServer` at **16**, one async function at **59**, and two async-arrow findings at **22** each. These values identify functions that are candidates for decomposition and review.

Exact repository-wide LOC, comment ratio, and duplication are generated by `scripts/t2-code-metrics.js`; the script should be run on the final branch and its JSON output committed under `docs/evidence/`.

## 4. System quality evidence

The available log analysis produced the following provider results:

| Provider | Fetches | Success | p50 | p95 |
|---|---:|---:|---:|---:|
| Notices | 112 | 84.8% | 13 ms | 46 ms |
| Traffic | 29 | 0% | — | — |
| Weather | 18 | 100% | 705 ms | 2339 ms |
| Air Quality | 16 | 100% | 916 ms | 1594 ms |

Traffic was unavailable in that run because the TomTom API key was not configured. Notices also experienced failures while the Authority server was unreachable. These are retained as quality evidence rather than hidden.

## 5. Data quality states

The dashboard specification separates readings into live, stale, and unavailable states. The final percentages must be generated from the final normalised reading stream rather than estimated from provider success rates. This distinction is important because a successful provider request does not automatically prove that every individual reading is fresh.

## 6. Trust and Authority workflow

Trust scores must come from the shared data layer. Authority approval rate and time-to-approve must come from the workflow-metrics endpoint or audit records. These values are not present in the currently available evidence, so this report intentionally marks them as **pending final repository/log run** rather than inventing them.

## 7. Testing

The existing project test run reported **30/30 checks passed (100%)**. This demonstrates the observed test suite passed completely. It is not a substitute for code coverage; a separate coverage command must produce the coverage percentage for the final branch.

## 8. Defects / quality issues

The defect log identifies traffic-provider configuration, Authority-server dependency failures, high complexity findings, missing coverage evidence, and missing extended reading metrics. Each item has an owner/action path and closure requires new evidence.

## 9. Reproducibility

Run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/t2-run.ps1
```

or directly:

```powershell
node scripts/t2-code-metrics.js
node scripts/t2-system-quality.js
```

The scripts write evidence under `docs/evidence/`.

## 10. Conclusion

T2 already has strong functional and provider-level evidence: the current test run passed all observed checks, weather and air-quality providers were fully successful in the captured run, and the log contains measurable latency and failure information. The remaining evidence must be generated against the final `t2-metrics` branch for repository-wide LOC/comment/duplication, coverage, reading-state percentages, trust-score distribution, and Authority workflow timing. Keeping those measurements explicitly pending until they are generated preserves the team's rule that every reported number must be traceable to a tool run or log.
